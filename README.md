# Redemption app

Backend-focused member rewards project. The monorepo, database foundation, and member frontend are implemented. The NestJS authentication/redemption endpoints and Redis mechanisms are subsequent work. The frontend includes an explicit browser demo and a separate API mode. `perk-site/` is the earlier standalone Sites demo and is not part of the workspace apps.

## Stack

- Node.js 22.12+, pnpm 11.25, Turborepo
- Next.js 16 App Router and React 19 (`apps/web`)
- NestJS 11 (`apps/api`)
- PostgreSQL and Prisma 6.19 (pinned to retain the planned schema-level `url`/`directUrl` configuration)
- Shared TypeScript contracts (`packages/types`)

## Start locally

```sh
pnpm install
cp apps/api/.env.example apps/api/.env
cp apps/web/.env.example apps/web/.env.local
docker compose up -d --wait
pnpm db:generate
pnpm db:deploy
```

Set `SEED_MEMBER_PASSWORD` in `apps/api/.env` to a development-only password with at least 12 characters, then:

```sh
pnpm db:seed
pnpm dev
```

Web: http://localhost:3000. API health: http://localhost:3001/api/health, also proxied at http://localhost:3000/api/health. Health indicates the process is running, not database readiness. The database module is ready for feature modules to import; the scaffold can start without database credentials.

`pnpm build` builds all packages. `pnpm typecheck` checks all packages. `pnpm db:validate` validates the schema. Prisma commands run from `apps/api` and load its `.env`. Builds need syntactically valid database URLs to generate the client but do not connect to PostgreSQL.

## Database

Four models: Member, Reward, RedemptionCode, Redemption. Redemption has unique member/code and member/idempotency-key constraints plus an index for stable newest-first history (createdAt, id). UUIDs are generated by Prisma; timestamps use PostgreSQL timestamptz. A null code expiry means no expiry.

The initial migration creates schema and indexes. The next migration enables RLS with no policies on all four tables and enforces positive maxUses, nonnegative usedCount, and usedCount <= maxUses. Supabase anonymous/authenticated roles cannot read or write these tables via the Data API. The API must use a trusted database role that bypasses RLS (Supabase postgres); never expose its credentials to the browser. Database constraints are groundwork; the atomic claim and transaction required for concurrent redemption are not implemented yet.

For a new migration after editing the schema:

```sh
pnpm db:migrate --name describe_change
```

Use `pnpm db:deploy` for applying committed migrations. Do not use `db push` as a replacement: it would omit the custom RLS and check constraints.

| Code | State | Reward |

| PLAY-IT-LOUD | Active, 3 uses | Music |
| TOO-LATE | Expired | Coffee |
| NOT-YET | Inactive | Shopping credit |
| FUTURE-PERK | Expires 30 days after first seed | Coffee |

Seeding is explicit, transactional, and repeatable. It prefers DIRECT_URL (the session pooler) when configured and uses a seed-only 60-second transaction timeout with a 10-second acquisition wait to accommodate remote database latency. API transaction defaults are unchanged. It preserves existing members, credentials, codes, counters, and redemption records; it does not reset used codes or extend expiration. Changing SEED_MEMBER_PASSWORD does not rotate existing passwords. Demo seeding refuses NODE_ENV=production. Run only against a development database.

## Supabase configuration (later)

Set DATABASE_URL to the transaction-pooler connection (port 6543, with `pgbouncer=true&connection_limit=1`) and DIRECT_URL to the session-pooler connection (port 5432). Copy the actual connection strings from your project's Connect panel. Keep credentials in ignored environment files. No Supabase or Upstash project is modified by this scaffold. Region and Vercel settings remain for deployment work.

## Local database lifecycle

`docker compose stop` stops PostgreSQL; `docker compose down` removes its container while retaining the named data volume. Only use `docker compose down -v` if you intentionally want to delete local database data.

## Database verification

Against a disposable, migrated and seeded local database, run:

```sh
pnpm --filter @redemption/api test:db
```

The suite checks seed password hashes and code states, RLS configuration, denied reads and writes for an untrusted role, counter constraints, and both redemption uniqueness constraints. It needs the seed password used for the existing fixtures and a local database role allowed to create a temporary test role. Test writes and role creation are rolled back. Do not run this role-creation suite against a production or shared Supabase database.

### Existing Supabase tables / P3005

The connected Supabase project already has unrelated tables in `public`. The app's local Supabase connection URLs therefore use `schema=redemption` on both DATABASE_URL and DIRECT_URL. Prisma creates and manages its tables and migration history in that dedicated schema, leaving existing public tables intact. Keep this parameter in deployment URLs too. No public tables are baselined, reset, or adopted by this app. New empty local databases can continue to use `schema=public`.

If you encounter P3005, inspect the target schema before proceeding. Do not mark the app's initial migration as applied unless its tables and constraints actually exist. The database tests documented above target the disposable local public schema, not the shared Supabase database.

## Member frontend

Run `pnpm --filter @redemption/web dev` and open http://localhost:3000. `/` redirects to `/redeem`; members without a browser session are sent to `/login`. The frontend supports responsive login, redemption, success confirmation, paginated history, reward detail dialogs, demo code help, sign-out, and recoverable error states.

**Explore demo** is the default login tab. Use `alex@perk.demo` / `perk1234` or choose another demo member. The demo password is intentionally public and separate from the seeded database password. Demo rewards are stored only in localStorage; the member session is stored in sessionStorage. Demo mode never calls the API or Supabase. Browser locking reduces overlapping demo writes where available, but the demo is not a production security or concurrency implementation. The guide can reset all demo records in this browser after an explicit reset confirmation.

**Member sign in** sends requests through the existing `/api/*` Next.js proxy to API_URL. These endpoints still need to be implemented in NestJS. The typed hand-written client expects:

| Endpoint | Request / response |
| --- | --- |
| POST /api/auth/login | `{ email, password }` → `{ member: { id, name, email } }`, with httpOnly JWT cookie |
| POST /api/auth/logout | Clear cookie; return 204 or JSON |
| POST /api/redemptions | `{ code }` + Idempotency-Key → shared RedemptionDto |
| GET /api/redemptions/me?limit=6&cursor=... | shared RedemptionHistoryResponse (`items`, `nextCursor`) |

Errors use `{ code, message }`. Cookies are included in every request; JWTs are never read or stored by frontend JavaScript. SessionStorage caches member display information only. Client route redirection is a usability feature, not authorization: the API must authenticate and scope every request. A 401 clears the browser session. Login does not yet use a server-side session restoration endpoint because the backend is not implemented.

TanStack Query handles mutations and cursor history. Requests time out after 15 seconds. A new UUID is created for each new redemption attempt and retained for explicit retries after network/server/in-progress errors; there are no automatic redemption retries. Changing the code starts another attempt. The current attempt key is held in component memory and does not survive a page reload. History queries are isolated by mode and member; sign-out clears query caches.

Frontend verification:

```sh
pnpm --filter @redemption/web test
pnpm --filter @redemption/web typecheck
pnpm --filter @redemption/web build
```

Tests cover demo login, member isolation, idempotent replay, duplicate and exhausted codes, expired/inactive/missing codes, rate limiting, cursor history, cookie/idempotency headers, session-expiry events, and network failure classification.
